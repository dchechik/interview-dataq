"Annotate with ee60f9f6 on VendorID" — the title. ee60f9f6 is the first 8 chars of a peer dataset's id (peer.dataset_id[:8]). The word annotate rather than join is chosen when the peer has fewer than 1/10th of your row count (suggesters.py:394) — i.e. it looks like a small lookup/reference table, so pulling it in decorates your rows rather than reshaping them. The proposed action is a left join, your dataset on the left, keyed on VendorID against the matching column on the right. That branch also gets a +0.15 score bump (capped at 0.95), which is why it's near the top of the list.

"join" — just the kind badge in the card's top-right corner. It tells you what applying the card will do (other kinds you'll see: enrich, aggregate, chart). Cards of kind join get the extra Edit button, which seeds the JoinPanel with left/right column and how so you can adjust before running.

"both columns are identity.key" — the rationale, and the whole basis for the match. The suggester ignores column names and pairs columns that share a semantic type marked joinable=True in the registry (backend/src/dataq/core/semantic.py:216). identity.key = "Identifier; high-cardinality identifier, a natural join key". Name equality only affects the score (0.9 if the two columns are also identically named, 0.7 otherwise), never whether the suggestion appears.

One caveat worth knowing: identity.key is the fallback type — CardinalityDetector (detectors.py:307) assigns it at confidence 0.55 to any text column where >90% of values are distinct and no specific detector fired. So "both are identity.key" means "both look like ids", not "these ids refer to the same thing"; two unrelated id columns will match. That's especially suspect here — VendorID in the taxi data is a 1–2 vendor code, and in the checked-in catalog it's an untyped BIGINT measure, so whatever dataset you're looking at got it typed as a key some other way (a manual pin, or a version where it's VARCHAR). Worth confirming that column's type on the dataset page before applying the join.

The logic (backend/src/dataq/plugins/builtin/timeline.py, _default_abnormality): the rule was inferred, never chosen. It looked for a rarity column — one whose semantic type is numeric.share or numeric.rarity, falling back to the literal names share/rarity for datasets profiled before those types existed — took the first one, and built share < 0.01 (or rarity > 0.99, since share counts down and rarity counts up). That column only exists if you ran agg.frequency and joined it back, which is the point: share is the fraction of rows carrying this value, so a small share means the event is unlike its neighbours. No rarity column meant no rule and no control at all — which is what you were hitting on the taxi data. The only editable part was the threshold; column and operator were rendered as static <code>.

What's editable now — the row reads Flag when [column] [op] [value] with a reset:

  • Column: any numeric column, plus — nothing — to turn flagging off. The rarity column is still what the backend picks when you haven't chosen; it's now a default rather than the only possibility.
  • Operator: < <= > >= == !=.
  • Threshold: unchanged in spirit, but it now accepts decimals (see below).

Backend changes: abnormality_op became AbnormalityOp | None (was str = "<", so a named rarity column would silently get < even when it needed >), and a new abnormality_enabled: bool lets the UI say "flag nothing" against a dataset where a rule would otherwise be inferred. _default_abnormality now defaults each part of the rule separately instead of as a block — so re-sending the inferred column while nudging the threshold keeps the "rare" label and the "fewer than 1% of rows share this country" rationale, which the old code dropped the moment a column was named explicitly. The rationale is withheld when you flip the operator, since "fewer than X% share this" is false once the rule flags the common values.

  2. Suggestion. VizSuggester (suggesters.py:73) proposes a map only when it finds both a geo.lat and a geo.lng, and pairs lats[0] with lngs[0] positionally — one map per dataset no matter how many coordinate pairs there are.

Net: a chart is reachable only if a suggester proposed it, and suggesters read semantic types, so a detection miss makes a whole chart type unreachable rather than merely unsuggested.
