Root cause: railway up tars the whole project directory. It does not read .dockerignore (that only applies after the context reaches the builder), and there was no .railwayignore. So the three untracked snapshot dirs went up the wire:

backend/data           463M
backend/data_old       491M
backend/data_old_0902  1.9G
backend/data_old_0902_01 491M

≈2.9 GB uncompressed → the 1,734,141,302-byte payload Cloudflare rejected.

What I changed:

  • .railwayignore (new, .railwayignore:1) — the upload-side ignore list: node_modules, .venv, caches, .git, **/data, **/data_old*, sample-data, *.duckdb/*.sqlite*, transcripts, .env, LOCAL_SETTINGS/LOCAL_USERS_FILE, plans/, docs/.
  • .dockerignore:17 — added **/data_old*. The existing **/data matched backend/data but not the data_old* siblings, so they'd have been copied into the image by COPY backend/.
  • .gitignore:15 — added data_old*/, data-from-railway/, dataq-data*.tgz so the snapshots stop showing up as untracked.

I deliberately avoided a data* glob — it would swallow backend/src/dataq and break the build. Patterns are data, **/data, **/data_old* only.

Verified by tarring the project with the same exclusions: 3.7 MB, down from 1.7 GB. Nothing tracked by git lives under any data* directory, and the deployed app reads from the Railway volume rather than the image, so nothing needed is excluded.

I didn't re-run the deploy — that's a push to your live service, so it's your call. make railway-deploy should now upload in a couple of seconds. Separately, those 2.9 GB of data_old* snapshots are still sitting in your working tree if you want to prune them.
