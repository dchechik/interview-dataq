# Import with an explicit column plan

## Context

Your `logon` import produced a `date` column of `VARCHAR` holding
`03/07/2011 08:07:29`. Nothing asked, nothing offered a choice, and the type was
frozen before you saw a single row. This makes that decision explicit, and lets
you change it before it is made.

### How types and roles are assigned today

**Physical type is decided once, early, invisibly, and permanently.** In
`services/operations.py::run_import`, everything hangs off one line:

```python
rel = reader.to_relation(conn, req.uri, params)      # DuckDB sniffs the file
columns = list(zip(rel.columns, [str(t) for t in rel.types], strict=True))
```

`rel.types` is DuckDB's sniffer's verdict. It is copied into `columns_schema` on
the version, into `ColumnStats.physical_type`, into `ColumnRow.physical_type`,
and it is what the data is written as. **Nothing afterwards can change it** —
`pin_column_type` writes only `semantic_type`, `confidence`, `pinned` and
`role`; re-profiling passes `physical_type` straight through; storage is
immutable per version. The only escape is a transform that *adds* a column
(`date` → `date_ts`), leaving the original text forever.

**Semantic type and role are derived afterwards**, in
`services/profiler.py::profile_columns`, from the already-written data. Three
branches, in order:

1. **Pinned** — a human edit wins outright; `role` is copied verbatim.
2. **Confident guess (≥ 0.5)** — `role` comes from the semantic type's registry
   default (`time.timestamp` → `time`), then the demotion added last week:
   `if role == "time" and not is_temporal(physical_type): role = "dimension"`.
3. **Otherwise** — `_fallback_role`, which is purely physical: temporal → time,
   numeric → measure, else dimension.

So role is a *judgement about* the physical type, and semantic type is a
judgement about the values. Both are late, cheap, and editable. Physical type is
early, irreversible, and invisible. **That asymmetry is the whole problem**: the
one decision you cannot revisit is the one you are never shown.

Two smaller consequences worth naming. The frontend sends only `{uri, name}`,
though `PreviewRequest` and `OperationRequest` both already accept `plugin_id`
and `params` — so `dateformat`, `timestampformat`, `delimiter` and `all_varchar`
exist and are unreachable. And `Preview` and `Import` are two independent
buttons: import never reads the preview, and is enabled without it.

**Decisions taken** (from the questions): the plan always appears with proposals
already filled in; physical type, date format, semantic type and role are all
editable; unparseable values become NULL and are reported in the preview rather
than failing the import; existing datasets are out of scope.

## The mechanism, measured

Three things were verified against DuckDB and your real files before choosing.

**Forcing the type at read time is not an option.** `types={'date':'TIMESTAMP'}`
aborts the entire import on the first unparseable row — including a legitimate
`n/a` — and `ignore_errors=true` **silently dropped 18 of 43 rows**, not just
the 3 bad ones. Neither is acceptable on an 850k-row file.

**Casting in the projection that materialises the version is.** Between
`to_relation` and `write_relation`, `SELECT try_strptime("date", fmt) AS "date",
… FROM view` yields a real `TIMESTAMP` named `date`, keeps every row, and turns
unparseable values into NULL — countable and reportable. It also works for every
reader, not just CSV.

**Text must be preserved for columns whose reading is ours to choose.** Given
`03/04/2016`, the sniffer returns `DATE` = 3 April without recording that it
guessed. `types={'when':'VARCHAR'}` keeps the text — forcing *to* text can never
fail — and then the chosen format decides:

```
default                          DATE      2016-04-03   (sniffer guessed)
types={'when':'VARCHAR'}         VARCHAR   03/04/2016   (text preserved)
    cast %m/%d/%Y  ->  2016-03-04        cast %d/%m/%Y  ->  2016-04-03
```

Cost is not a concern. Sniffing plus 200 rows plus format inference measured
**68 ms** on `logon.csv` (5 columns) and **198 ms** on the taxi CSV (19). One
caveat that sets a parameter: at 200 sampled values `logon.date` reads as
**ambiguous**, because every day in the first 200 rows is ≤ 12. At 1,000
distinct values it resolves to `%m/%d/%Y %H:%M:%S` in **89 ms**. So the plan
samples ~2,000 distinct values per text column — enough to answer the question
rather than punt it to you.

## What changes

### 1. A plan endpoint — `POST /api/sources/plan`

Returns, per column: the sniffed type, sample values, the proposed target type
and cast, the semantic guess with its rationale, the proposed role, the format
candidates with any conflict, and — when a cast is proposed — the share of
sampled values that would parse.

It is built by **running the real profiler on a sample**, not by reimplementing
it: `compute_stats` → `run_detectors` → `profile_columns` over a `LIMIT`-ed
relation, plus `infer_formats`/`ambiguous` from `core/datefmt.py`. That is the
property that makes the preview trustworthy — it shows what the import will
decide because it is the same code.

A column is marked `decision_required` only when the data genuinely cannot
settle it: two formats fitting equally well and disagreeing. Everything else
arrives pre-decided.

### 2. The import applies the plan

`OperationRequest.params` for `op="import"` gains `columns: list[ColumnPlan]`,
each carrying `name`, `target_type`, `format`, `semantic_type`, `role`. Then in
`run_import`:

- columns whose plan needs our own parsing are read as text
  (`types={col: 'VARCHAR'}`, new `CsvParams.column_types`);
- `write_relation` gets a cast projection instead of `SELECT *`;
- `columns` is re-derived from the projected relation, so `physical_type` is the
  post-cast type everywhere it is recorded;
- per-column parse failures are counted, logged, and written to the existing
  `ColumnProfile.warning`, which already renders as the "check format" badge;
- the plan's semantic types and roles are applied as **pinned**, via the
  `previous=` argument `profile_and_store` already takes.

One guard is needed. `profile_columns` branch 1 copies a pinned role verbatim
and **skips the `is_temporal` demotion** — so a pinned `role="time"` on a text
column would recreate the exact bug fixed last week. The plan is validated
server-side: `role="time"` requires a temporal target type, and semantic types
and roles are checked against `SEMANTIC_TYPES` and the `ColumnRole` literal,
neither of which `pin_column_type` validates today.

### 3. The import UI becomes preview → adjust → confirm

`frontend/src/pages/DatasetsPage.tsx` — the import section becomes a small
component with the column plan as a table: column, what was found, **import as**
(dropdown), the format (dropdown, when temporal), **meaning**, **role**, and the
sample values. An ambiguous column shows both readings with a worked example
(`03/07/2011 → 7 March or 3 July`) and blocks Import until chosen. Everything
else is pre-filled, so the normal path is: look, click Import.

Follows the existing consequence-then-confirm precedents — `ConfirmRun` in
`AgentPage.tsx` (its `ask` → `pending` → `send` split is exactly this shape) and
`DeleteDataset` in `DatasetPage.tsx`.

Three fixes come with it: `Import` becomes reachable only through the plan
rather than being a parallel button; `accepted.dataset_id` is currently
discarded, so a successful import will navigate to the new dataset; and
`JobProgress` calls `onDone` **during render**, firing repeatedly — it moves
into an effect.

### 4. Role becomes editable, and correctable afterwards

`ColumnRow` in `DatasetPage.tsx` renders role as a read-only badge even though
`api.pinColumnType` already accepts a role nobody passes. It becomes a dropdown,
so a role can be corrected without re-importing.

### How types and roles are assigned today

**Physical type is decided once, early, invisibly, and permanently.** In
`services/operations.py::run_import`, everything hangs off one line:

```python
rel = reader.to_relation(conn, req.uri, params)      # DuckDB sniffs the file
columns = list(zip(rel.columns, [str(t) for t in rel.types], strict=True))
```

`rel.types` is DuckDB's sniffer's verdict. It is copied into `columns_schema` on
the version, into `ColumnStats.physical_type`, into `ColumnRow.physical_type`,
and it is what the data is written as. **Nothing afterwards can change it** —
`pin_column_type` writes only `semantic_type`, `confidence`, `pinned` and
`role`; re-profiling passes `physical_type` straight through; storage is
immutable per version. The only escape is a transform that *adds* a column
(`date` → `date_ts`), leaving the original text forever.

**Semantic type and role are derived afterwards**, in
`services/profiler.py::profile_columns`, from the already-written data. Three
branches, in order:

1. **Pinned** — a human edit wins outright; `role` is copied verbatim.
2. **Confident guess (≥ 0.5)** — `role` comes from the semantic type's registry
   default (`time.timestamp` → `time`), then the demotion added last week:
   `if role == "time" and not is_temporal(physical_type): role = "dimension"`.
3. **Otherwise** — `_fallback_role`, which is purely physical: temporal → time,
   numeric → measure, else dimension.

judgement about the values. Both are late, cheap, and editable. Physical type is
early, irreversible, and invisible. **That asymmetry is the whole problem**: the

"""What to store each column as, decided before the import rather than after.

A column's physical type is settled by DuckDB's sniffer the moment the file is
read, is copied into every record of the dataset, and cannot be changed
afterwards -- storage is immutable per version and nothing but a transform that
*adds* a column can produce a different type. Semantic type and role, by
contrast, are derived later, from data already written, and stay editable
forever.

That asymmetry is the problem this module exists to fix: the one decision that
cannot be revisited is the one nobody is shown. So the decision is proposed
first, with its evidence, and the user gets to change it before it is made.

The proposal is built by running the *real* profiler over a sample rather than
by reimplementing it. That is deliberate, and it is the property that makes the
preview worth trusting: what it shows is what the import will do, because it is
the same code.
"""

from __future__ import annotations

from typing import Any, Literal

from pydantic import BaseModel, Field

from ..core.datefmt import FormatCandidate, ambiguous, infer_formats
from ..core.profile import ColumnProfile, is_temporal
from ..core.semantic import SEMANTIC_TYPES
from ..core.types import ColumnRole
from ..query.compiler import quote_ident

# Types a column may be stored as. Deliberately short: these are the ones a
# reader can plausibly get wrong and a person can meaningfully choose between.
TargetType = Literal["VARCHAR", "BIGINT", "DOUBLE", "BOOLEAN", "DATE", "TIMESTAMP"]
TARGET_TYPES: tuple[str, ...] = (
    "VARCHAR", "BIGINT", "DOUBLE", "BOOLEAN", "DATE", "TIMESTAMP")

# Rows read to build the proposal. Enough to answer the question rather than
# punt it: at 200 sampled values a MM/DD/YYYY column reads as ambiguous, because
# every day in the first 200 rows of a real export can be <= 12. At 1,000 it
# resolves, in 89ms. The whole proposal costs ~70ms on a 5-column file and
# ~200ms on a 19-column one.
PLAN_SAMPLE_ROWS = 2_000

# Preview rows returned alongside the proposal.
PREVIEW_ROWS = 8


class PlanError(ValueError):
    """The plan cannot be carried out as written."""


class ColumnPlan(BaseModel):
    """What to do with one column. The editable part of a proposal."""

    name: str
    # None means "leave it as the reader produced it".
    target_type: TargetType | None = None
    # How to read the text, when the target is temporal and the source is not.
    # A strptime format, or epoch:s / epoch:ms / epoch:us.
    format: str | None = None
    semantic_type: str | None = None
    role: ColumnRole | None = None


class ColumnProposal(BaseModel):
    """A proposed plan for one column, with the evidence behind it."""

    name: str
    source_type: str = Field(description="What the reader would produce, untouched")
    proposed: ColumnPlan
    sample_values: list[Any] = []
    # Why this is proposed, in a sentence, for the person deciding.
    rationale: str = ""
    # Temporal candidates, best first. Offered as choices when more than one.
    formats: list[FormatCandidate] = []
    # Share of sampled non-null values the proposed cast would keep, when it
    # casts at all. Reported rather than enforced: a stray 'n/a' should cost one
    # value, not the import.
    parse_rate: float | None = None
    # True when the data genuinely cannot settle the question and a person must.
    decision_required: bool = False
    conflict: str | None = None


class ImportPlan(BaseModel):
    reader: str
    sampled_rows: int
    columns: list[ColumnProposal]
    rows: list[list[Any]] = []

    @property
    def undecided(self) -> list[str]:
        return [c.name for c in self.columns if c.decision_required]

# SQL
# --------------------------------------------------------------------------- #
def _epoch_expr(col: str, unit: str) -> str:
    divisor = {"s": "1", "ms": "1000.0", "us": "1000000.0"}[unit]
    return f"to_timestamp(CAST({col} AS BIGINT) / {divisor})"


def cast_expr(name: str, plan: ColumnPlan, source_type: str) -> str | None:
    """SQL for one column, or None when it should be passed through untouched."""
    if plan.target_type is None or plan.target_type == source_type.upper():
        return None
    col = quote_ident(name)

    if plan.target_type in ("TIMESTAMP", "DATE") and plan.format:
        if plan.format.startswith("epoch:"):
            expr = _epoch_expr(col, plan.format.split(":", 1)[1])
        else:
            literal = "'" + plan.format.replace("'", "''") + "'"
            expr = f"try_strptime(CAST({col} AS VARCHAR), {literal})"
        # try_strptime yields a TIMESTAMP; a DATE target needs the narrowing.
        return f"CAST({expr} AS DATE)" if plan.target_type == "DATE" else expr

    # try_cast rather than cast: a value that will not convert becomes NULL
    # instead of ending the import. Which values those were is measured and
    # reported, so the failure is loud without being fatal.
    return f"try_cast({col} AS {plan.target_type})"


def cast_projection(plans: dict[str, ColumnPlan], columns: list[tuple[str, str]]) -> str:
    """The SELECT list that materialises the version.

    Casting here rather than at read time is what keeps the import survivable.
    Asking DuckDB for `types={'date':'TIMESTAMP'}` aborts the whole read on the
    first unparseable row -- one 'n/a' in 850,000 -- and `ignore_errors` answers
    that by silently dropping rows, which was measured at 18 lost from 43. A
    projection over the already-read relation cannot drop anything.
    """
    parts: list[str] = []
    for name, source_type in columns:
        plan = plans.get(name)
        expr = cast_expr(name, plan, source_type) if plan else None
        parts.append(f"({expr}) AS {quote_ident(name)}" if expr else quote_ident(name))
    return ", ".join(parts) if parts else "*"


def text_columns(plans: dict[str, ColumnPlan], columns: list[tuple[str, str]]) -> list[str]:
    """Columns the reader must hand back as text for the plan to be applied.

    Given 03/04/2016 the sniffer returns a DATE and does not record that it
    chose between March and April. Once it has converted, the evidence is gone
    and the other reading is unreachable -- so a column whose reading is the
    user's to make has to arrive unconverted.
    """
    out = []
    for name, source_type in columns:
        plan = plans.get(name)
        if plan and plan.format and not is_temporal(source_type):
            continue  # already text; nothing to preserve
        if plan and plan.format and is_temporal(source_type):
            out.append(name)
    return out

def validate_plan(plans: list[ColumnPlan], known: set[str]) -> None:
    """Reject a plan that cannot mean what it says.

    ``pin_column_type`` validates neither semantic types nor roles, so a plan
    arriving over HTTP is the first place either is checked.
    """
    seen: set[str] = set()
    for plan in plans:
        if plan.name not in known:
            raise PlanError(
                f"no column named {plan.name!r}; the file has: "
                f"{', '.join(sorted(known)[:12])}"
            )
        if plan.name in seen:
            raise PlanError(f"two plans for the same column: {plan.name!r}")
        seen.add(plan.name)

        if plan.semantic_type and SEMANTIC_TYPES.get(plan.semantic_type) is None:
            raise PlanError(
                f"{plan.name}: unknown semantic type {plan.semantic_type!r}")
        if plan.role and plan.role == "time":
            # profile_columns copies a pinned role verbatim, so a pinned
            # role="time" on a text column recreates the VARCHAR - INTERVAL
            # failure this whole feature exists to prevent. Refused at the door.
            target = plan.target_type or ""
            if not is_temporal(target):
                raise PlanError(
                    f"{plan.name}: role 'time' needs a date or timestamp column, "
                    f"but it is being imported as {target or 'whatever the reader '
                    'produces'}. Set the type to TIMESTAMP, or pick another role."
                )
        if plan.format and plan.target_type not in ("TIMESTAMP", "DATE"):
            raise PlanError(
                f"{plan.name}: a format only applies when importing as a "
                f"TIMESTAMP or DATE, not {plan.target_type or 'the reader default'}"
            )

# building the proposal
# --------------------------------------------------------------------------- #
def _temporal_target(formats: list[FormatCandidate]) -> str:
    """TIMESTAMP when the format carries a time, DATE when it is a day."""
    best = formats[0]
    if best.format.startswith("epoch:"):
        return "TIMESTAMP"
    return "TIMESTAMP" if any(c in best.format for c in ("%H", "%I")) else "DATE"


def _propose(profile: ColumnProfile, raw_values: list[Any]) -> ColumnProposal:
    """Turn one profiled column into a proposal."""
    source_type = profile.physical_type
    proposal = ColumnProposal(
        name=profile.name,
        source_type=source_type,
        proposed=ColumnPlan(
            name=profile.name,
            semantic_type=profile.semantic_type,
            role=profile.role,
        ),
        sample_values=(profile.stats.sample_values[:6] if profile.stats else []),
    )

    temporal_meaning = SEMANTIC_TYPES.matches_any(profile.semantic_type, ("temporal",))
    formats = infer_formats(raw_values) if raw_values else []

    # The column reads as dates but is not stored as one -- the reported case.
    if temporal_meaning and not is_temporal(source_type) and formats:
        proposal.formats = formats
        proposal.proposed.target_type = _temporal_target(formats)  # type: ignore[assignment]
        proposal.proposed.format = formats[0].format
        proposal.proposed.role = "time"
        proposal.parse_rate = formats[0].success_rate
        proposal.rationale = (
            f"holds dates as text ({formats[0].label}); importing it as "
            f"{proposal.proposed.target_type} makes it usable as a time axis"
        )

    # The reader already converted it -- but from text that read two ways, so
    # which one it chose was a guess nobody recorded.
    elif is_temporal(source_type) and formats and ambiguous(formats):
        proposal.formats = formats
        proposal.proposed.target_type = source_type.upper()  # type: ignore[assignment]
        proposal.proposed.format = formats[0].format
        proposal.rationale = (
            "the reader converted this itself, choosing between two readings "
            "that both fit"
        )

    elif is_temporal(source_type):
        proposal.rationale = "already a date or timestamp"
    elif profile.semantic_type:
        proposal.rationale = f"detected as {profile.semantic_type}"

    if formats and ambiguous(formats):
        proposal.decision_required = True
        proposal.conflict = formats[0].conflict
    return proposal


def build_plan(conn, reader_cls, uri: str, params: dict[str, Any]) -> ImportPlan:
    """Propose how every column should be imported, with the evidence.

    Runs the same profiler the import runs, over a sample, so the preview and
    the outcome cannot disagree.
    """
    from .profiler import compute_stats, profile_columns

    reader = reader_cls()
    rel = reader.to_relation(conn, uri, reader_cls.parse_params(params))
    columns = list(zip(rel.columns, [str(t) for t in rel.types], strict=True))
    if not columns:
        raise PlanError(f"{uri} has no columns")

    view = "_dq_plan_sample"
    conn.execute(f"CREATE OR REPLACE TEMP VIEW {view} AS "
                 f"SELECT * FROM ({rel.sql_query()}) LIMIT {PLAN_SAMPLE_ROWS}")
    sampled = conn.execute(f"SELECT count(*) FROM {view}").fetchone()[0]

    stats = compute_stats(conn, view, columns, PLAN_SAMPLE_ROWS)
    profiles = profile_columns(stats)
    raw = _raw_text_sample(conn, reader_cls, uri, params, columns)

    proposals = [_propose(p, raw.get(p.name, [])) for p in profiles]
    rows = [list(r) for r in
            conn.execute(f"SELECT * FROM {view} LIMIT {PREVIEW_ROWS}").fetchall()]
    conn.execute(f"DROP VIEW IF EXISTS {view}")

    return ImportPlan(reader=reader_cls.id, sampled_rows=int(sampled),
                      columns=proposals, rows=rows)


def _raw_text_sample(conn, reader_cls, uri: str, params: dict[str, Any],
                     columns: list[tuple[str, str]]) -> dict[str, list[Any]]:
    """The columns as unconverted text, for format inference.

    Needed because a column the reader already turned into a DATE has lost the
    evidence of how it was written -- and that evidence is the only way to tell
    whether the reading was forced or guessed. Readers that cannot hand back
    text (parquet, JSON) get the empty dict, which honestly says the question
    was not asked.
    """
    if "all_varchar" not in reader_cls.Params.model_fields:
        return {}
    try:
        raw = reader_cls().to_relation(
            conn, uri, reader_cls.parse_params({**params, "all_varchar": True}))
        select = ", ".join(quote_ident(n) for n, _ in columns)
        rows = conn.execute(
            f"SELECT {select} FROM ({raw.sql_query()}) LIMIT {PLAN_SAMPLE_ROWS}"
        ).fetchall()
    except Exception:  # noqa: BLE001 -- a diagnostic must not break the preview
        return {}
    out: dict[str, list[Any]] = {}
    for i, (name, _) in enumerate(columns):
        seen: list[Any] = []
        distinct: set[Any] = set()
        for row in rows:
            v = row[i]
            if v is None or v in distinct:
                continue
            distinct.add(v)
            seen.append(v)
        out[name] = seen
    return out

                 columns: list[tuple[str, str]], job_ctx: JobCtx) -> dict[str, str]:

    The cast is deliberately survivable -- try_cast and try_strptime answer a
    value they cannot convert with NULL rather than ending the import, because
    one 'n/a' in 850,000 rows should not cost the file. That makes the count the
    only evidence anything was lost, so it is measured and attached to the
    column rather than left for someone to notice.
    """

    for name, source_type in columns:
        plan = plans.get(name)
        expr = cast_expr(name, plan, source_type) if plan else None
        if expr is not None:
            measured.append((name, expr))

        return {}

    parts = []
    for i, (name, expr) in enumerate(measured):
        col = quote_ident(name)
        parts.append(f"count({col}) AS n{i}")
        parts.append(f"count({expr}) AS ok{i}")

/**
 * Importing a dataset, with the column types shown before they are frozen.
 *
 * A column's physical type is decided by the reader the moment the file is
 * read, is copied into every record of the dataset, and can never be changed
 * afterwards — the only escape is a transform that adds a second column beside
 * it. Meaning and role, by contrast, are worked out later and stay editable
 * forever. So the one decision that cannot be revisited was the one nobody was
 * ever shown, which is how a column of dates ends up stored as text.
 *
 * The plan arrives already decided. The normal path is to look at it and press
 * Import; the only thing that stops is a column the data genuinely cannot
 * settle, and then it says which readings are on offer and what each would mean.
 */

const TARGET_TYPES: TargetType[] = [
  'VARCHAR', 'BIGINT', 'DOUBLE', 'BOOLEAN', 'DATE', 'TIMESTAMP',

const ROLES: ColumnRole[] = ['dimension', 'measure', 'time', 'key', 'geo', 'ignore']

/** Friendlier than the SQL spelling, for a table a non-technical user reads. */
const TYPE_LABELS: Record<string, string> = {
  VARCHAR: 'text',
  BIGINT: 'whole number',
  DOUBLE: 'number',
  BOOLEAN: 'true/false',
  DATE: 'date',
  TIMESTAMP: 'date + time',
}

function typeLabel(sql: string): string {
  const key = sql.toUpperCase()
  return TYPE_LABELS[key] ?? sql.toLowerCase()
}

"""Usernames and passwords, and the sessions they buy.

The shared token in :mod:`dataq.api.auth` is the right shape for one person on
one laptop, and the wrong shape for a URL you send to a colleague: there is
nothing to type into a browser, no way to tell two people apart, and revoking
access means changing the secret for everyone.

This adds the smallest thing that fixes that. A fixed list of users, each with a
password hash; a login endpoint that exchanges a password for a session token;
and a token the browser can keep. Everyone sees the same datasets -- the point
is to keep the instance off the public internet, not to model permissions.

Two decisions worth stating, because both could reasonably have gone the other
way in a prototype:

* **Passwords are hashed, not stored.** scrypt, from the standard library, with
  a per-password salt. A hard-coded list is fine; a hard-coded *password* would
  mean the repository, every clone of it, and every terminal that ever printed
  the config all hold the credential itself.
* **Sessions are signed, not stored.** A token carries its own username and
  expiry with an HMAC over both, so there is no session table to grow, and a
  restart does not log everybody out -- the signing key lives in the data
  directory, beside the data it protects.
"""

from __future__ import annotations

import base64
import hashlib
import hmac
import json
import os
import secrets
import time
from pathlib import Path

# scrypt parameters. These are the interactive-login numbers from the original
# paper: ~16MB and a few tens of milliseconds, which is nothing to a person
# logging in and a great deal to someone working through a stolen hash.
SCRYPT_N = 1 << 14
SCRYPT_R = 8
SCRYPT_P = 1
SALT_BYTES = 16

SESSION_PREFIX = "dq1"
DEFAULT_SESSION_HOURS = 24 * 14


def _b64(raw: bytes) -> str:
    return base64.urlsafe_b64encode(raw).decode().rstrip("=")


def _unb64(text: str) -> bytes:
    return base64.urlsafe_b64decode(text + "=" * (-len(text) % 4))


# --------------------------------------------------------------------------- #
# passwords
# --------------------------------------------------------------------------- #
def hash_password(password: str, salt: bytes | None = None) -> str:
    """``scrypt$<salt>$<hash>``, safe to commit and to print."""
    salt = salt or secrets.token_bytes(SALT_BYTES)
    derived = hashlib.scrypt(password.encode(), salt=salt, n=SCRYPT_N,
                             r=SCRYPT_R, p=SCRYPT_P)
    return f"scrypt${_b64(salt)}${_b64(derived)}"


def verify_password(password: str, stored: str) -> bool:
    """Check a password against a stored hash, in constant time.

    A malformed or empty hash is a failure rather than an error: this runs on an
    unauthenticated path, so a bad entry in the user list must not become a way
    to crash the login endpoint.
    """
    try:
        scheme, salt_b64, expected = stored.split("$", 2)
        if scheme != "scrypt":
            return False
        salt = _unb64(salt_b64)
    except (ValueError, TypeError):
        return False
    derived = hashlib.scrypt(password.encode(), salt=salt, n=SCRYPT_N,
                             r=SCRYPT_R, p=SCRYPT_P)
    return hmac.compare_digest(_b64(derived), expected)


def parse_users(spec: str | None) -> dict[str, str]:
    """``name:hash`` entries, separated by commas or newlines.

    Hashes contain ``$`` and base64, never ``:``, so splitting on the first
    colon is unambiguous.
    """
    users: dict[str, str] = {}
    for entry in (spec or "").replace("\n", ",").split(","):
        entry = entry.strip()
        if not entry or entry.startswith("#"):
            continue
        name, _, digest = entry.partition(":")
        if name.strip() and digest.strip():
            users[name.strip()] = digest.strip()
    return users


def authenticate(username: str, password: str, users: dict[str, str]) -> bool:
    """Whether these credentials are good.

    An unknown username is still checked against a dummy hash. Returning early
    would make a wrong username measurably faster than a wrong password, which
    is a free list of who has an account.
    """
    stored = users.get(username)
    if stored is None:
        verify_password(password, _DUMMY_HASH)
        return False
    return verify_password(password, stored)

# the wrong-password path.

# --------------------------------------------------------------------------- #
def session_secret(data_dir: Path, configured: str | None = None) -> bytes:
    """The key sessions are signed with.

    Kept in the data directory rather than generated per process, so restarting
    the server -- or a code deploy -- does not sign everyone out. Created on
    first use with owner-only permissions.
    """
    if configured:
        return configured.encode()
    path = Path(data_dir) / "session_secret"
    if path.exists():
        return path.read_bytes().strip()
    path.parent.mkdir(parents=True, exist_ok=True)
    secret = secrets.token_hex(32).encode()
    path.write_bytes(secret)
    try:
        os.chmod(path, 0o600)
    except OSError:
        pass  # a filesystem that does not do modes; the directory still guards it
    return secret

      <h2><span class="num">01</span>The shape</h2>
      <p class="lede">Two ideas carry most of the system. Everything else is an application of them.</p>

      <h3>Plugins are heterogeneous in contract, homogeneous in execution</h3>
      <p>Every plugin declares two independent things. Its <b>kind</b> is what it consumes and produces, which fixes its Python interface. Its <b>mode</b> is how the runtime must run it, which fixes its scheduling. The two are orthogonal: an extractor may be a regex (<code>pushdown</code>) or an LLM call (<code>external</code>), and nothing downstream can tell which ran.</p>

      <div class="scroller">

      <h3>The semantic layer is the metadata that makes suggestion automatic</h3>
      <p>A column's <em>meaning</em> (<code>net.ip</code>, <code>geo.lat</code>, <code>money.amount</code>) is tracked separately from its storage type, in a hierarchy, so a rule written for <code>categorical</code> applies to <code>geo.country_iso2</code> for free. Two datasets are joinable when they share a meaning, not a column name — that is the whole reason join and chart suggestion are not hand-wired.</p>

    <section id="import">
      <h2><span class="num">02</span>Import</h2>
      <p class="lede">The path that decides what everything downstream is allowed to do.</p>

      <div class="flow">
        <div class="step"><b>Plan</b><span>services/import_plan.py</span></div>
        <div class="arrow">→</div>
        <div class="step"><b>Read</b><span>plugins/builtin/readers.py</span></div>
        <div class="arrow">→</div>
        <div class="step"><b>Cast &amp; write</b><span>storage/parquet.py</span></div>
        <div class="arrow">→</div>
        <div class="step"><b>Profile</b><span>services/profiler.py</span></div>
      </div>

      <p>A file's column types are settled by DuckDB's sniffer the instant it is read, copied into every record of the dataset, and can never be changed afterwards — storage is immutable per version, and the only escape is a transform that adds a second column beside the first. Meaning and role, by contrast, are derived later and stay editable forever.</p>

      <div class="note">
        <span class="tag">The load-bearing asymmetry</span>
        <p>The one decision that could not be revisited was the one nobody was shown. That is how a column of dates ends up stored as text, and it is what the import plan exists to fix.</p>
      </div>

      <p>So import now proposes a plan and waits: per column, what the reader found, what it will be stored as, how a date will be read, its meaning and its role.       <p>Casting happens in the projection that materialises the version, never at read time. At read time it cannot be survived: <code>types={'date':'TIMESTAMP'}</code> aborts the whole import on the first bad row, and <code>ignore_errors</code> answers that by silently dropping rows — measured at 18 lost from 43. A projection cannot drop anything.</p>

    <section id="profiling">
      <h2><span class="num">03</span>Types, meaning, role</h2>
      <p class="lede">Three different questions that are easy to conflate, and expensive to conflate.</p>

      <div class="scroller">
        <table>
          <thead><tr><th>Property</th><th>Decided by</th><th>When</th><th>Changeable</th></tr></thead>
          <tbody>
            <tr><td>Physical type</td><td>the reader, or the import plan</td><td>at read</td><td>no — only by re-import</td></tr>
            <tr><td>Semantic type</td><td>detectors, ranked by confidence</td><td>after writing</td><td>yes, by pinning</td></tr>
            <tr><td>Role</td><td>the semantic type's default, then storage</td><td>after writing</td><td>yes, by pinning</td></tr>
          </tbody>
        </table>
      </div>

      <p>Role assignment has three branches, in priority order: a pin wins outright; otherwise a guess above 0.5 confidence supplies the role its semantic type declares; otherwise a purely physical fallback. Both of the first two branches then pass through one guard.</p>

      <div class="note warn">
        <span class="tag">The bug this guard exists for</span>
        <p>A <code>VARCHAR</code> holding <code>03/07/2011 08:07:29</code> <em>means</em> a timestamp, and detection says so correctly. It still cannot be a time axis: subtracting an interval from text is a type error. Without the demotion, every time-based plugin picked the column up and failed deep inside DuckDB with <code>No function matches -(VARCHAR, INTERVAL)</code> and forty lines of candidate operators, naming neither the column nor the remedy.</p>
      </div>

      <p>Counts come from the whole table rather than the sample. Distinct counts are the reason: sampled, they cap at the sample size, so any column with more distinct values than that looks like a per-row identifier — and "as many distinct values as rows" is exactly the test that tells a user id from an event id. A 38,230-user column was being excluded from entity detection entirely.</p>

      <ul class="pointers">
        <li><span class="path">services/profiler.py</span><span class="what"><code>compute_stats</code>, <code>run_detectors</code>, <code>profile_columns</code>, <code>_storable_role</code></span></li>

    <section id="storage">
      <h2><span class="num">04</span>Storage &amp; catalog</h2>
      <p>Two backends behind one protocol. <b>Parquet</b> is the default: immutable part files per version, resumable writes, portable to S3. <b>DuckDB tables</b> is the single-file option — mount one volume, or copy the file. The catalog is always SQLite in WAL mode, deliberately <em>not</em> in the warehouse: it takes many small transactional writes, which is DuckDB's weak spot.</p>

      <p>A dataset is addressable as a SQL relation through <code>sql_source()</code> — <code>read_parquet('lake/&lt;id&gt;/v3/*.parquet')</code> or a quoted table name. Everything else composes on top of that string.</p>

      <ul class="pointers">
        <li><span class="path">storage/base.py</span><span class="what">the protocol: <code>write_relation</code>, <code>open_writer</code>, <code>sql_source</code>, <code>drop</code>, <code>drop_dataset</code></span></li>
        <li><span class="path">catalog/models.py</span><span class="what">datasets, versions, columns, jobs, steps, dashboards</span></li>
        <li><span class="path">catalog/repo.py</span><span class="what">the only module that talks to SQLite; additive column migration at startup</span></li>

    <section id="query">
      <h2><span class="num">05</span>The query layer</h2>
      <p><code>QuerySpec</code> is a small typed IR — filters, one time bucket, nine aggregates, group-by, order, limit — compiled to DuckDB SQL with every identifier checked against the resolved schema and every literal bound as a parameter. It is 351 lines in total, and its restraint is deliberate: no window functions, no joins, no subqueries, no raw expressions.</p>

      <p>Three sanctioned escape hatches exist for what the IR will not express, all of them authored by trusted plugin code rather than by a user: <code>AggregatePlan.derive</code> for window functions, <code>SqlPlan.add</code> for per-column expressions, and <code>POST /api/query/sql</code> for reading, gated by DuckDB's own parser to a single <code>SELECT</code>.</p>

      <ul class="pointers">
        <li><span class="path">query/spec.py</span><span class="what">the IR</span></li>
        <li><span class="path">query/compiler.py</span><span class="what"><code>compile</code>, <code>quote_ident</code>, filter rendering, time parts</span></li>

    <section id="plugins">
      <h2><span class="num">06</span>Plugins</h2>
      <p>One registry, many surfaces. A plugin's single Pydantic <code>Params</code> model becomes the request schema, the OpenAPI doc, the auto-rendered UI form and the agent's tool schema — there is no second place where plugin metadata is written down, so a backend plugin arrives with a working UI and no frontend change.</p>

      <p><code>Accepts</code> declares preconditions (semantic types, dataset kinds, minimum rows) and drives both the UI's action list and the agent's choices. Matching is hierarchical, so <code>("categorical",)</code> matches <code>geo.country_iso2</code>.</p>

      <ul class="pointers">

    <section id="jobs">
      <h2><span class="num">07</span>Jobs</h2>
      <p>Mode decides everything about execution. <code>pushdown</code> is one DuckDB statement. <code>batch</code> streams Arrow with part-file checkpointing and resume from a durable row watermark. <code>external</code> adds an async pool, a result cache, retries, cost accounting and a budget cap. <code>inspect</code> runs in the request thread and never creates a job.</p>

      <p>The runtime owns the projection, not the plugin, so a transform cannot accidentally drop columns or change cardinality. It also enforces post-conditions: <code>ParseCheck</code> measures, on a sample before writing, how many non-null inputs produced non-null outputs — because every parsing expression DuckDB offers answers failure with <code>NULL</code>, so a wrong format otherwise <em>succeeds</em> and writes a column of nothing.</p>

      <ul class="pointers">
        <li><span class="path">jobs/executor.py</span><span class="what">mode dispatch, <code>build_projection</code>, <code>run_checks</code>, <code>build_join_source</code></span></li>

      <h2><span class="num">08</span>Suggestions</h2>
      <p>A <code>Suggestion</code> carries an <code>action</code> that is a literal API request body. The UI renders it as a button; the agent invokes it directly. Nothing suggests in prose only — which is what keeps "the tool suggests things" from degenerating into a wall of advice.</p>

      <p>Five suggesters now: clean-up (parse this text date), features, visualisations, aggregates, joins. The join suggester is the payoff of the semantic layer — it proposes joins across datasets by shared meaning, and ranks a join onto a small aggregate higher because that is an annotation.</p>

    <section id="viz">
      <h2><span class="num">09</span>Charts &amp; timeline</h2>
      <p><code>ChartSpec</code> is a typed grammar-of-graphics subset — mark plus encodings — resolved server-side against the semantic layer and the query's real output types, then compiled to Vega-Lite in the browser. <code>raw_vega_lite</code> is the escape hatch. Structurally it is the humblest object here — a QuerySpec with a time column, no aggregation, ordered by time — so it fits the renderer registry as a fourth entry rather than needing new machinery.</p>

    <section id="features">
      <h2><span class="num">10</span>Behavioural features</h2>
      <p>Per-entity, time-windowed statistics attached to every row: how often this user did this in the last 30 days, how common the activity is overall, how long since they last did it. Written as expressions, parsed into a typed IR that the API and agent exchange.</p>

      <p>Two steps, because the intermediate is worth having on its own. <code>agg.features</code> builds a feature table you can chart and query; <code>enrich.features</code> attaches it back on a composite key and adds the per-row features no grouped table can hold. Cost tracks the number of distinct sorts, not the number of features — five sharing a window cost 0.7s on 5M rows where six across three windows cost 6.3s.</p>

      <ul class="pointers">

      <p>Accounts with scrypt-hashed passwords; signing in exchanges a password for a session token signed with a key kept in the data directory, so a redeploy does not sign everybody out. The older shared token still works alongside, which is what scripts and the deploy docs use.</p>

    <section id="critique">
      <h2>Critique</h2>
      <p class="lede">Ranked by what I would actually fix first. Several of these are mine — added on top of something rather than in place of it.</p>

      <div class="finding">
        <header><span class="rank">01</span><h3>Two overlapping date-format mechanisms</h3><span class="sev honesty">honesty</span></header>
        <p>The import plan re-reads the raw text, infers formats and asks the user. <code>sniffer_ambiguities</code> + <code>_sniffer_warnings</code> also re-read the raw text, infer formats, and record a warning — for the case the plan now handles up front. I added the second without removing the first, and had to patch the overlap by excluding planned columns from the warning.</p>
        <div class="fix"><b>Cut:</b> delete <code>sniffer_ambiguities</code>, <code>_which_was_chosen</code> and <code>_sniffer_warnings</code>. About 90 lines and one whole re-read of every imported file, replaced by a step that already runs.</div>
      </div>

      <div class="finding">
        <header><span class="rank">02</span><h3>Two sources of truth for physical types</h3><span class="sev correctness">correctness</span></header>
        <p><code>VersionRow.columns_schema</code> and <code>ColumnRow.physical_type</code> both store the type of every column, written from the same tuple list but read by different code — the query compiler resolves through the first, profiling and every plugin through the second. Nothing keeps them honest, and a bug that desynchronised them would be very hard to see.</p>
        <div class="fix"><b>Cut:</b> keep <code>columns_schema</code> as the schema of record (it exists before profiling) and derive <code>ColumnProfile.physical_type</code> from it on read, or drop it and have <code>resolve_source</code> read columns. Either way, one writer.</div>
      </div>

      <div class="finding">
        <header><span class="rank">03</span><h3><code>quote_ident</code> exists three times; the temporal-type tuple six</h3><span class="sev clutter">clutter</span></header>
        <p>Identical <code>quote_ident</code> in <code>query/compiler.py</code>, <code>storage/duck.py</code> and inline in <code>TransformCtx.col</code>. The <code>("TIMESTAMP","DATE","TIME")</code> prefix test is written out in six places despite <code>is_temporal()</code> existing to hold it — including in <code>_fallback_role</code>, twelve lines away from a call to it.</p>
        <div class="fix"><b>Cut:</b> one <code>quote_ident</code> in a shared module; every temporal check through <code>is_temporal</code>. Small, but this is exactly the duplication that lets two of them drift.</div>
      </div>

      <div class="finding">
        <header><span class="rank">04</span><h3>Declared features that do nothing</h3><span class="sev honesty">honesty</span></header>
        <p><code>dry_run</code> is on <code>OperationRequest</code>, has a full <code>DryRunResult</code> model and a <code>dry_run_rows</code> setting, and is not implemented. <code>agg.frequency.min_count</code> is a documented parameter that is never read — a user setting it gets no filtering and no error. <code>SqlPlan.replace</code> is implemented in the executor and used by zero plugins.</p>
        <div class="fix"><b>Cut:</b> delete all three. A parameter that silently does nothing is worse than a missing one, because it invites you to rely on it. <code>replace</code> would earn its place if a cast-in-place transform used it — that is the honest way to keep it.</div>
      </div>

      <div class="finding">
        <header><span class="rank">05</span><h3>Two god modules</h3><span class="sev clutter">clutter</span></header>
        <p><code>api/app.py</code> is 681 lines with all 34 routes inside one <code>_register_routes</code> function. <code>services/operations.py</code> is 579 lines holding four op handlers plus profiling, plan application, cast measurement, sniffer warnings and dataset cleanup. Both are navigable only by search.</p>
        <div class="fix"><b>Cut:</b> FastAPI routers per area (sources, datasets, query, jobs, auth, agent); one module per op under <code>services/ops/</code>. No behaviour change, and the diff of the next feature stops touching a 600-line file.</div>
      </div>

      <div class="finding">
        <header><span class="rank">06</span><h3>Five column-shaped models</h3><span class="sev clutter">clutter</span></header>
        <p><code>ColumnStats</code>, <code>SemanticGuess</code>, <code>ColumnProfile</code>, <code>ColumnPlan</code>, <code>ColumnProposal</code> — plus <code>ColumnRow</code> in the catalog and a hand-written mirror of most of them in <code>api/types.ts</code>. Each is justified in isolation; together they are a lot of shapes for one concept, and the TypeScript copies drift silently because nothing checks them against the OpenAPI document.</p>
        <div class="fix"><b>Cut:</b> run the existing <code>npm run gen:types</code> in CI and import the generated types where the hand-written aliases duplicate them. The models can stay; the second, unchecked copy of them should not.</div>
      </div>

      <div class="finding">
        <header><span class="rank">07</span><h3>Suggester scores are ungoverned magic numbers</h3><span class="sev clutter">clutter</span></header>
        <p>Roughly two dozen literal scores from 0.5 to 0.97 spread across five suggesters, each locally sensible, none aware of the others. The final ordering a user sees is emergent, there is no test that asserts it, and tuning one suggester silently reorders another's output.</p>
        <div class="fix"><b>Cut:</b> a small ordered enum of intents — <em>fix this</em>, <em>look at this</em>, <em>build this</em> — with scores derived from it, and one test that pins the top three for two representative datasets.</div>
      </div>

      <div class="finding">
        <header><span class="rank">08</span><h3>Five thousand lines of frontend, no tests</h3><span class="sev correctness">correctness</span></header>
        <p>Every frontend bug this project has had was found by driving a real browser by hand. The map rendering nothing, the SPA fallback masking a missing chunk, <code>onDone</code> firing during render — all real, all invisible to the 582 backend tests.</p>
        <div class="fix"><b>Add, don't cut:</b> Vitest for the pure logic that already exists in isolation (<code>dateFormats</code>, the plan edit reducer, <code>withToken</code>), and one Playwright smoke test that imports a file and asserts the resulting types. Not a suite — a floor.</div>
      </div>

      <div class="finding">
        <header><span class="rank">09</span><h3>Pins are per-version and propagate implicitly</h3><span class="sev correctness">correctness</span></header>
        <p>A pin lives on a <code>ColumnRow</code>, so it belongs to one version, and reaches the next only because every op remembers to pass <code>previous=</code>. Forgetting that argument silently discards every human correction on the dataset. It also produced a real bug: the pinned branch copied a role verbatim, skipping the guard that stops a text column claiming to be a time axis.</p>
        <div class="fix"><b>Cut:</b> move pins to the dataset rather than the version. They are statements about a column's meaning, which does not change because a transform added a different column.</div>
      </div>

      <div class="finding">
        <header><span class="rank">10</span><h3><code>ColumnProfile.warning</code> is one string doing several jobs</h3><span class="sev clutter">clutter</span></header>
        <p>It carries the sniffer's ambiguity note, and now also the count of values a cast could not convert. It can hold one of them, so the second overwrites the first, and the UI can only render it as prose.</p>
        <div class="fix"><b>Cut:</b> a list of typed notes — <code>{kind, message}</code> — or, once finding 01 is done, just the cast losses, which is the only producer left.</div>
      </div>
