Add the timeline view

A timeline answers a different question from a chart. A chart asks what shape
the data has; a timeline asks what happened, to this thing, in what order. You
reach for it when the individual events matter -- one user's session, one
address's activity, one vehicle's shifts.

Structurally it is the humblest thing here: a QuerySpec with a time column, no
aggregation, ordered by time. Everything else is presentation, so it fits the
existing renderer registry as a fourth entry rather than needing new machinery.

TimelineSpec, alongside ChartSpec
  Which column is the headline, which attributes ride along, which of those are
  emphasised, and which values make an event worth a second look. Resolved
  against the query's real output the same way charts are: a missing time or
  abnormality column is an error naming what the query does return, while a
  missing attribute is dropped -- losing one chip is recoverable, losing the
  timeline is not.

Abnormality falls out of work already done
  agg.frequency produces share and rarity; joined back onto the events they came
  from, every row carries how common its own value is. So "share < 0.01" means
  "this login came from somewhere we almost never see logins from" -- the spec's
  own worked example, finally visible. When a dataset has such a column the rule
  is inferred, with a rationale, because a highlight the reader cannot explain
  looks arbitrary.

Subjects, not identifiers
  Attribute defaults come from the semantic layer, but identity type alone is
  not enough: event_id is identity-typed and unique per row, and filtering by it
  yields a timeline of one event. A subject is something you have several events
  for, so a column with roughly as many distinct values as rows stays a plain
  attribute rather than a pivot.

The view
  Time in a fixed left column, headline where the eye lands, detail as chips,
  sticky day headings, and a rose tint plus badge on anything the rule trips.
  Clicking a subject chip pivots the whole timeline to that value. Suggested
  automatically, and ranked above the charts on an annotated dataset.

Two things fixed on the way
  The auth fixture drew a fresh random IP per row, so src_ip was unique and
  behaved like a primary key. Real hosts make many requests; it now draws from a
  bounded pool, which is both more realistic and what makes subject filtering
  demonstrable.

  test_a_charts_query_can_be_saved_as_a_dataset compared two orderings of
  ORDER BY n DESC, whose ties have no defined order. The changed fixture made
  two countries tie and exposed it; it now compares counts.

Verified in a browser against auth events joined to a country frequency table:
200 events, 3 flagged, all from the 1%-weighted country, and a chip click
narrowing to one user's 108 events.

What's there

A Timeline tab on any dataset with a timestamp (/datasets/:id/timeline). It reads as a list of events: time in a fixed left column, headline where the eye lands, attributes as chips, sticky day headings.

Structurally a timeline turned out to be the humblest thing in the codebase — a QuerySpec with a time column, no aggregation, ordered by time. So it slots into the renderer registry as a fourth entry rather than needing new machinery, and TimelineSpec sits alongside ChartSpec with the same resolve-against-real-output contract.

Abnormality fell out of work already done. agg.frequency produces share/rarity; joined back onto its source, every event carries how common its own value is. So when a dataset has that column the rule is inferred automatically — share < 0.01, labelled rare, with the rationale shown so the highlight never looks arbitrary. On the annotated auth data: 200 events, 3 flagged, all from the 1%-weighted country. That's the spec's "how common is a login from France" made visible.

Filtering works two ways: explicit filter rows, or clicking a subject chip to pivot ("show me only this user" — 200 events → that user's 108).

One judgment call worth flagging

Semantic type alone wasn't enough to decide what you can pivot on. event_id is identity.key, same as a user ID — but it's unique per row, so filtering by it gives a timeline of one event. A subject is something you have several events for, so a column with roughly as many distinct values as rows stays a plain attribute. That's why user_email, src_ip and country are clickable but event_id isn't.

Two bugs fixed on the way

The auth fixture drew a fresh random IP per row, making src_ip behave like a primary key — real hosts make many requests. It now draws from a bounded pool, which is both more realistic and what makes subject filtering demonstrable.

That change then exposed a latent test fragility: test_a_charts_query_can_be_saved_as_a_dataset compared two orderings of ORDER BY n DESC, whose ties have no defined order. Two countries tied and it failed. It now compares counts.

For the aggregation part you're planning

The timeline already works on join- and aggregate-derived datasets — that's how the annotated fixture is built, and the tests cover it. What it doesn't yet do is offer to build the annotation for you: today you have to run agg.frequency and the join yourself before the abnormality rule has anything to read. A "annotate this dataset with rarity, then show me the timeline" one-click path is the natural seam for whatever you define next.

## Deployment

One container serves `/api` and the built SPA, with all state under one volume:

```bash
make docker && make docker-run     # http://localhost:8000
```

Config is entirely environment-driven — see `.env.example`. For a hosted deploy
(Railway, Fly), mount a volume at `/data`; set `DATAQ_STORAGE=duckdb` if you would
rather have a single file to back up than a directory of Parquet.

## Development

```bash
make test     # pytest, parameterised over both storage backends
make lint     # ruff + mypy, tsc + oxlint
make types    # regenerate frontend types from the live OpenAPI document
```

## The agent

The chat agent binds its tools to the **service layer**, not to HTTP, so it and the
API cannot drift apart — they are two front ends over the same functions. Tool calls
stream to the UI as they run, so the user watches the work rather than waiting on a
verdict.

Two permission scopes exist. `full` (the chat agent, driven by a human who can see
and cancel jobs) can create aggregates, joins and transforms. `read_only` — handed to
any agent-*backed plugin* — can query, profile and suggest but has no job-creating
tools at all, which is the recursion guard: a plugin cannot spawn unbounded work.

Before any request is sent the UI prices the run — tokens in the first request
(counted by the API when a key is present, approximated otherwise) and a ceiling
for the whole loop — and asks. The user is paying, so the decision is theirs.

Set `ANTHROPIC_API_KEY` to enable it. Everything else runs without one.

## Status

Implemented and tested: import, profiling and semantic typing, transforms in all
three execution modes, the query layer, charts and maps, aggregates, joins, the
dashboard, and the agent.

The agent's tool surface and loop mechanics are covered by tests using a scripted
model client (tool dispatch, the `tool_result` round-trip, parallel calls, refusals,
the turn cap) — including the spec's cybersecurity workflow driven end to end through
agent tools. The loop has **not** been exercised against the live model; that needs an
API key.

Known gaps, in rough priority order:

- `dry_run` is defined on `OperationRequest` and documented as the way to preview an
  expensive extraction, but is not implemented yet. It matters most for `external`
  plugins, which is exactly where it is missing.
- The `external` transform ships one real plugin (`extract.entities`); it has been
  exercised against a fake client, not a live model.
- Job resume is implemented and tested at the storage layer, but nothing yet
  automatically restarts an interrupted job on startup — resume is a manual re-submit.
- The frontend has no test suite.
- Single-process only. Multi-worker deployment needs `DATAQ_STORAGE=parquet` and an
  out-of-process job runner.

I checked rather than shipped it, because the difference is user-visible: there's nothing to gitignore, and a fresh clone of this repo needs linking again. Both the README and docs/DEPLOY.md now say so.

I also verified every make target the README names actually exists in the Makefile — all eleven do.

Two stale bits fixed while I was there: the frontend layout listing was missing Timeline, Ask, ChartEditor and ChartInspector, and the status summary didn't mention the chart grammar, timeline, or the Railway deployment.

One flag: the deploy instructions are written from the Railway docs and the local verification I did (entrypoint, $PORT binding, auth, restore) — but no actual Railway deploy has been run, since that needs your account. The first real railway up is still the true test.
