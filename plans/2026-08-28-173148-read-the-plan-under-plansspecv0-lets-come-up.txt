⏺ Fair — the plugin layer was hand-waved. Let me work it out properly.

  The core design decision: plugins are heterogeneous in contract but 
  homogeneous in execution. Every plugin declares a kind (what it
  consumes/produces) and independently an execution mode (how the runtime must
  run it). Normalization and extraction turn out to be the same interface at
  different modes; visualization is different because it's inspect-mode and
  returns a document rather than data.

⏺ Plan rewritten around the plugin layer. Direct answers to what you asked:

  How plugins span very different stages — every plugin declares two independent
  things: a kind (its Python interface — what it consumes/produces) and a mode
  (how the runtime must run it). Six kinds, four modes, and they're orthogonal.
  Visualization is different from extraction because it's inspect-mode: it
  returns a document (a spec), synchronously, and never touches the job system.
  Everything that produces data goes through the job path regardless of stage.

  Long-running jobs — pushdown becomes one DuckDB statement; batch streams Arrow
  batches and flushes a part file every N batches, recording a rows_committed
  watermark; external adds an async pool, retries, and a persistent result
  cache. Resume = skip committed parts. This is the concrete reason Parquet-lake
  is the default layout even though single-file DuckDB is easier to host.

  API to trigger a specific plugin — yes, one uniform endpoint: POST 
  /api/operations {op, plugin_id, inputs, params} → 202 {job_id}, with GET 
  /api/plugins?applicable_to={dataset_id} enumerating what's legal and each
  plugin's params_schema defining the body. That single response also generates
  the UI forms and the agent's tool schemas — plugin metadata is written down in
  exactly one place. POST /api/inspect is the synchronous twin for
  viz/suggesters.

  Standard interface for normalize vs. extract — they're the same kind
  (Transform: DatasetVersion → DatasetVersion), differing only by mode, which
  selects sql() vs process(batch) vs async process_rows(). Output contract is
  identical, so nothing downstream knows which was used. Aggregation is
  genuinely separate because it changes cardinality — it's a QuerySpec generator
  producing a new Dataset.

  LLM-powered plugins — mode="external" plus eight runtime-provided facilities
  so authors don't hand-roll them: injected client, enforced
  concurrency/batching, automatic result caching (keyed on plugin version +
  params + model + input, so re-running over a superset only pays for new rows),
  declared structured output, per-step cost accounting with max_cost_usd,
  prompt-cache-friendly layout, row-level failure isolation, and opt-in Batch
  API. A plugin that is itself an agent gets ctx.tools scoped to the read-only
  service subset — it can't call operations.create, so it can't spawn unbounded
  jobs. There's also a dry_run flow that samples 1000 rows and extrapolates cost
  before a non-technical user commits to a $40 extraction.

  I also split Stage 2 out so the job machinery lands before the plugins that
  depend on it, and added tests for the parts most likely to be subtly wrong

     DataQ v0 — Implementation Plan

     Context

     plans/spec_v0 describes DataQ: make 1–10GB dataset analysis easy for
     non-technical users, via a pipeline of pluggable components (import →
     normalize → aggregate → extract → join → visualize), with every capability
     reachable by both a UI and an in-app AI agent.

     The repo is currently empty apart from that spec. This plan sets up the
     project from scratch and builds the first vertical slice. Priority order
     the user set:

     1. The framework — plugin contracts, registry, execution model, metadata
        layer, lineage. This is the actual deliverable.
     2. A few hours of work — a side project. A thin but complete vertical
        slice, not a half-built layer cake.
     3. Prototype on real datasets afterwards — NYC taxi and cyber/auth logs
        first.

     Decisions made with the user:
     - Backend Python (FastAPI + DuckDB), frontend React + TypeScript + Vite.
     - Storage: Parquet-lake layout by default, but pluggable so a single
       .duckdb file can hold everything (easier remote hosting).
     - v0 scope = import + profile + query + charts + joins & aggregates. The
       agent follows (Stage 6), but its contract is designed in from the start.
     - First datasets: NYC taxi (geo/time/scale) and cyber-auth logs (IP,
       country, rarity annotation).

     ---

     Storage: DuckDB critique and the resulting design

     DuckDB is the right engine — vectorised, zero-ops, reads Parquet/CSV/JSON
     natively, handles 1–10GB on a laptop trivially, pushes predicates into
     Parquet. Two limitations shape the design:

     - Single-writer. One process may hold a .duckdb file for writing. Fine for
       one FastAPI process; it breaks the moment a background worker runs in a
       second process.
     - A .duckdb file is an opaque blob. Checkpointing a version means copying a
       table; you can't hand a version to another tool, and object storage
       isn't a natural fit.

     So DuckDB is the query engine, not necessarily the storage format. Split
     the two:

     class StorageBackend(Protocol):
         def write(self, ref: VersionRef, rel: duckdb.DuckDBPyRelation) ->
     StoredRef: ...
         def write_part(self, ref: VersionRef, n: int, batches) -> PartRef: ...
      # for resumable jobs
         def sql_source(self, ref: StoredRef) -> str: ...   # a SQL-referencable
     expression
         def drop(self, ref: StoredRef) -> None: ...

     - ParquetStorage(base_uri) — default. COPY (…) TO 
       '{base}/{dataset}/{version}/part-*.parquet'; sql_source →
       read_parquet('…/*.parquet'). Immutable versions = free checkpoints, part
       files = resumable jobs, and base_uri can become s3://… (via httpfs) with
       no other code change.
     - DuckDBTableStorage(db_path) — the easy-to-host option. CREATE TABLE 
       "{dataset}__v{n}" AS …; sql_source → the table name. Whole warehouse is
       one file: mount one volume on Railway/Fly, or scp it.

     Selected by DATAQ_STORAGE=parquet|duckdb; the same test suite runs against
     both. Known constraint to document: out-of-process job workers require
     parquet mode, because duckdb mode holds a single write lock.

     Catalog stays separate, in SQLite (catalog.sqlite, SQLModel) in both modes.
     It takes many small transactional writes (jobs, steps, progress
     heartbeats, column metadata) — exactly DuckDB's weak spot, and putting it
     in the warehouse file would make the write lock the bottleneck for the
     whole API.

     The plugin layer

     The central idea

     Plugins are heterogeneous in contract, homogeneous in execution.

     Every plugin declares two independent things:

     - kind — what it consumes and produces. This determines its Python
       interface. A visualizer and an extractor are genuinely different, so they
       get different interfaces.
     - mode — how the runtime must execute it. This determines whether it runs
       in the request thread or as a checkpointed background job, and what
       facilities it's handed.

     Separating these is what keeps the framework small. The stage a plugin
     belongs to (import/normalize/extract/aggregate) does not determine how it
     runs — an extractor can be a cheap regex (pushdown) or an LLM call
     (external), and the runtime handles both without the plugin knowing the
     difference.

     Execution modes

     Mode: pushdown
     Runs: One DuckDB SQL statement
     Facilities the runtime provides: Query construction, progress callback
     Typical latency: seconds–minutes
     ────────────────────────────────────────
     Mode: batch
     Runs: Job worker, streams Arrow batches
     Facilities the runtime provides: Batch iteration, part-file checkpointing,
     progress
     Typical latency: minutes
     ────────────────────────────────────────
     Mode: external
     Runs: Job worker, async pool
     Facilities the runtime provides: Concurrency limit, retry/backoff, result 
     cache, cost accounting, budget cap, structured output, row-level failure
     isolation
     Typical latency: minutes–hours
     ────────────────────────────────────────
     Mode: inspect
     Runs: Request thread, synchronous
     Facilities the runtime provides: Read-only catalog + sampled query access
     Typical latency: milliseconds

     inspect is the answer to "visualization is very different": visualizers and
     suggesters don't produce data at all — they produce a document (a spec, a
     list of suggestions). They're synchronous, cheap, and never create a job.
     Everything that produces data goes through the job path.

     The six kinds

     class Plugin(Protocol):
         id: str                    # "normalize.ip", "extract.llm_entities"
         kind: PluginKind
         mode: ExecMode
         version: str               # participates in cache keys
         title: str
         Params: type[BaseModel]    # ONE pydantic model -> request schema + 
     OpenAPI
                                    #   + auto-rendered UI form + agent tool 
     schema
         accepts: Requirements      # e.g. semantic_types=["net.ip"], 
     min_rows=...
         produces: Produces         # columns / semantic types / dataset kind 
     added

     accepts/produces is what makes plugins discoverable: given a dataset's
     column semantic types, the registry answers "what can I do with this?" —
     driving both the UI's action list and the agent's choices.

     ┌─────┬────────────┬──────────────────────────────────────────┬───────────┐
     │  #  │    Kind    │                Interface                 │  Usual    │
     │     │            │                                          │   mode    │
     ├─────┼────────────┼──────────────────────────────────────────┼───────────┤
     │ 1   │ Reader     │ to_relation(conn, uri, params) ->        │ pushdown  │
     │     │            │ DuckDBPyRelation                         │           │
     ├─────┼────────────┼──────────────────────────────────────────┼───────────┤
     │ 2   │ Detector   │ detect(col, stats, sample) ->            │ inspect   │
     │     │            │ list[SemanticGuess]                      │           │
     ├─────┼────────────┼──────────────────────────────────────────┼───────────┤
     │ 3   │ Transform  │ DatasetVersion → DatasetVersion          │ any       │

     Transform — one interface for normalize, extract, and annotate

     This is the direct answer to "is there a standard interface for 
     normalization vs extraction?" — yes, they are the same kind. Both take a
     dataset version and return a new version with columns added or rewritten.
     They differ only in mode, which selects which of three methods the plugin
     implements:

     # mode = "pushdown"  — normalization, regex extraction, type coercion
     def sql(self, ctx: TransformCtx) -> SqlPlan:
         # returns projected/added SQL expressions; DuckDB does all the work
         return SqlPlan(add={"src_ip_canon":
     f"lower(trim({ctx.col('src_ip')}))"})

     # mode = "batch"     — needs a Python library (geoip lookup, custom 
     parsing)
     def process(self, batch: pa.RecordBatch) -> pa.RecordBatch: ...

     # mode = "external"  — LLM / network calls
     async def process_rows(self, rows: list[dict], ctx: ExternalCtx) ->
     list[dict]: ...

     The runner dispatches on mode; the output contract is identical in all
     three cases (a new DatasetVersion + a Step recording lineage). Everything
     downstream — versioning, profiling, the UI, the agent — is unaware of which
     mode was used.

     Aggregator is a separate kind because it changes cardinality: it produces a
     new Dataset, not a new version of an existing one. It is expressed as a
     QuerySpec generator, which makes it pushdown by construction and keeps it
     composable with the query layer.

     Long-running jobs

     Every non-inspect invocation becomes a Job containing one or more Steps.
     Dispatch by mode:

     - pushdown — build one statement, COPY (…) TO parquet or CREATE TABLE AS.
       Progress via DuckDB's progress callback.
     - batch — stream rel.record_batch(100_000) → plugin → writer. Checkpoint 
       every N batches by flushing a part file and recording rows_committed on
       the step. Resume = skip committed parts.
     - external — same streaming, plus an asyncio pool bounded by
       plugin.max_concurrency, retry with backoff, and a persistent result
       cache. Checkpointing matters most here: these are the runs that take an
       hour and cost money.

     Resumability is exactly why the Parquet-lake layout is the default: each
     committed part is an immutable file, so resume is "read the watermark, skip
     those parts, continue."

     Job state: queued → running → (paused) → succeeded | failed | cancelled,
     carrying progress{rows_done, rows_total, pct, eta}, logs[], and for
     external also cost{calls, tokens_in, tokens_out, usd, cache_hits}.

     JobRunner is a protocol. v0 impl = in-process ThreadPoolExecutor plus an
     asyncio loop for external, writing job/step rows to the catalog. Swappable
     for RQ/Celery/Temporal without touching a single plugin.

     Triggering a specific plugin — one uniform endpoint

     Yes, there is a single API for this, and its uniformity is what makes it
     agent-usable:

     GET  /api/plugins?kind=&applicable_to={dataset_id}
          -> [{id, kind, mode, title, params_schema, accepts, produces,
     cost_class}]

     POST /api/operations
          { op: "import"|"transform"|"aggregate"|"join",
            plugin_id: "extract.llm_entities",
            inputs: [{dataset_id, version?}],
            params: {...},                    # validated against plugin.Params
            output: {name?, materialize: bool},
            dry_run?: true, max_cost_usd?: 5.0 }
          -> 202 {job_id, step_id}

     GET  /api/jobs/{id}          # status, progress, cost, logs
     GET  /api/jobs/{id}/stream   # SSE
     POST /api/jobs/{id}/cancel

     POST /api/inspect            # synchronous twin for inspect-mode plugins
          {plugin_id, dataset_id, params} -> the document (VizSpec / suggestions
     / guesses)

     GET /api/plugins tells you what can go in plugin_id; each plugin's
     params_schema tells you what goes in params. The UI's dynamic form renderer
     and the agent's tool schemas are both generated from that one response —
     there is no second place where plugin metadata is written down.

     dry_run: true runs the plugin over a sample (default 1000 rows) and returns
     sample output plus an extrapolated cost/time estimate without creating a
     version. This is a first-class flow, not an afterthought — it's how a
     non-technical user avoids launching a $40 extraction by accident.

     LLM-powered plugins

     A plugin backed by Claude is just mode="external". Everything hard about it
     is provided by the runtime so plugin authors never hand-roll it:

     1. Injected client. Plugins receive ctx.model — never construct their own
        client. Centralizes auth/model choice/retries and lets tests inject a
        fake.
     2. Concurrency & batching. Plugin declares batch_size and max_concurrency;
        the runner enforces them. The plugin just writes async def 
        process_rows(rows, ctx).
     3. Caching — automatic and mandatory. Key = sha256(plugin_id, 
        plugin_version, params, model_id, input_payload), stored in a DuckDB
        cache table. Re-running an extraction over a superset of rows costs only
        the new rows. This is the single biggest thing that makes LLM plugins
        practical.
     4. Structured output. The plugin declares an output Pydantic model; the
        runner uses output_config={"format": …}, so results arrive
        guaranteed-shaped. No parsing in plugin code.
     5. Cost accounting & budget. Every call is attributed to the step;
        max_cost_usd aborts cleanly with partial results committed.
     6. Prompt-cache friendliness. Stable prefix (system + few-shot) carries
        cache_control; volatile row data goes last; many rows per call.
     7. Row-level failure isolation. A row that fails after retries yields NULL
        plus an _error column instead of killing the job. stop_reason == 
        "refusal" is a row-level outcome, not a crash.
     8. Batch API opt-in. A plugin may declare supports_batch_api: true; for
        large non-interactive runs the job uses client.messages.batches (50%
        cost) and polls.

     Agent-powered plugins. A plugin whose implementation is itself a tool-using
     agent (e.g. a suggester that explores the data before proposing
     aggregates) is the same external mode, additionally handed ctx.tools — the
     read-only subset of the service layer (run_query, profile_dataset,
     list_datasets). Recursion guard: that tool set excludes operations.create,
     so a plugin can never spawn unbounded jobs. The top-level chat agent and an
     agent-powered plugin share one tool registry, differing only in permission
     scope.

     API details already checked against current guidance: Python anthropic SDK,
     model claude-opus-5, thinking: {type: "adaptive"}, streaming, @beta_tool +
     client.beta.messages.tool_runner.

     Registration & third-party plugins

     Built-ins register via decorator at import. Third-party plugins register
     via the dataq.plugins Python entry-point group, so pip install 
     dataq-plugin-geoip adds capability with zero core changes.

     Frontend plugin registry (the mirror image)

     Visualizers are inspect-mode: the backend returns a VizSpec = {renderer,

     only a genuinely new rendering technology needs frontend code.

     Query layer (backend/src/dataq/query/)

     QuerySpec — a structured IR compiled to DuckDB SQL:

     { source: DatasetRef | JoinRef,

     QuerySpec — one IR, four producers. A raw-SQL escape hatch (POST 
     /api/query/sql) runs on a read-only DuckDB connection with a statement-type
     check. Joins materialize as kind=join datasets backed by a view, so
     downstream steps treat them like any other dataset.

  The thing that shaped the design

  A browser's <input type="file"> gives you file contents, not a path. DuckDB
  reads data files in place on the server. So the naive implementation — open a
  native file dialog, take file.name — produces a path the server can't open,
  and every import fails.

  So Browse… lists the server's filesystem and returns a real path. That's also
  the right answer for the 1–10 GB target: zero copy. Upload sits alongside it
  in the same dialog for when the file genuinely is only on the viewer's
  machine.

  What you get

  The path input now has a Browse… button. The dialog shows root shortcuts,
  clickable breadcrumbs, .. navigation, file sizes, and a badge for which reader
  will handle each file. Only directories and files a registered reader can
  actually read are listed — no scrolling past .DS_Store. Picking a file fills
  the path, names the dataset after the filename, and previews it in one click.
  Esc closes it.

  Security, since this lists a filesystem over HTTP

  Browsing is confined to DATAQ_BROWSE_ROOTS (colon-separated). Unset, it
  defaults to your home + working directory — right when the server is your
  laptop, and something an operator overrides for a hosted deploy. resolve()
  runs before the containment check, so traversal (../secret), absolute escapes
  (/etc) and symlinks pointing outside a root are all refused with a 403. The
  parent link disappears at a root boundary rather than offering a way out. Each
  of those is a separately tested case.

  Uploads reduce the client-supplied filename to a sanitized basename, never
  clobber an existing file, stream to disk in 1 MB chunks, and delete the
  partial file if the size cap trips.

  Two bugs fixed along the way

  The API client was setting Content-Type: application/json unconditionally,
  which would have made every multipart upload unparseable. And DatasetPage was
  using useMemo for a side effect (fetching semantic types) — that's now a
  proper cached query.

  The two rules that turn the DAG into a tree

  The lineage was already recorded in Step.inputs/outputs — the work was
  deciding what counts as an edge:

  A transform is not an edge. normalize.ip produces a new version of auth, not a
  child of it. Only aggregate and join create new datasets. Getting this wrong
  would have made auth its own child.

  A join has two parents, but a tree node has one. auth_annotated comes from
  auth ⋈ auth_frequency. It nests under its left input and names the other 
  parent inline (via join + auth_frequency, clickable) — the second edge stays
  visible rather than being silently dropped, which is the failure mode I most
  wanted to avoid.

  Two robustness cases, both tested

  Deleting a parent surfaces its children as roots rather than making them
  vanish from the page entirely. And a cycle is broken rather than recursed into
  — operations shouldn't ever build one, but an infinite recursion in the
  dataset list is a bad way to find out.

     edit
     A grammar of graphics for DataQ, and closing the rollup ↔ chart divide

     Context

     Two questions prompted this.

     1. Why do charts diverge from rollup actions? They mostly shouldn't.
     Exploration confirms AggregateCtx and VizCtx are field-for-field identical
     dataclasses, both plugin kinds build the same QuerySpec with dataset="" for
     the service to bind, and for the timeline case the two queries differ only
     in the aggregate list and the LIMIT:

     # viz.timeseries                          # agg.time_rollup
     time_bucket=TimeBucket(col, interval)     time_bucket=TimeBucket(col,
     interval, part=p.part)
     select=[count *, avg(m)]                  select=[count *, sum(m), avg(m)]
     limit=10_000                              limit=1_000_000

     Only one difference is real: an aggregate changes cardinality, so it
     becomes a new materialized dataset — and in doing so it inherits semantic
     types (pinned) and becomes joinable. It joins the semantic graph. A chart
     renders and produces nothing the catalog can reason about. That distinction
     is worth keeping. Everything else is accidental duplication, and it
     already causes visible capability gaps: agg.time_rollup supports cyclical
     time parts, viz.timeseries does not — so today you can materialize "busiest
     hour of day" but you cannot chart it, even though the query IR and
     compiler fully support it.

     2. Can we have a grammar of graphics? We already ship one — Vega-Lite 6.4.3
     is a grammar of interactive graphics. The problem is not the engine, it is
     that we hide it behind opaque JSON:

     spec: dict[str, Any] = {}   # "Renderer-specific payload"

     Nothing types it, nothing validates it, and Python and TypeScript share no
     definition of it. Concretely: nothing verifies that a field named in an 
     encoding exists in the query's output columns, so a typo or a renamed alias
     fails silently as an empty chart. The couplings that can break this way
     are already load-bearing and stringly-typed — "bucket",
     "lat"/"lng"/"value", and avg_{measure} reconstructed identically in both
     the query and the encoding.

     Intended outcome: presentation becomes a typed, validated, editable object
     that the semantic layer can resolve — and a chart and a rollup become two
     things you can toggle between rather than two separate worlds.

     Approach

     Separate "what to query" from "how to draw", and make both first-class 
     typed objects.

     Panel  =  QuerySpec (exists, typed)  +  ChartSpec (new, typed)

     ChartSpec — a Vega-Lite-shaped IR

     New backend/src/dataq/core/chart.py, deliberately a subset of Vega-Lite's
     vocabulary so it compiles 1:1:

     Mark    = Literal["bar", "line", "area", "point", "tick", "rect", "arc",
     "boxplot"]
     Channel = Literal["x", "y", "color", "size", "shape", "opacity", "theta",
     "detail",
                       "row", "column", "tooltip"]

     class Encoding(BaseModel):
         field: str
         type: EncodingType | None = None    # inferred from the semantic layer 
     when omitted
         aggregate: AggFunc | None = None
         bin: bool | int | None = None
         sort: str | None = None
         title: str | None = None
         stack: bool | None = None

     class ChartSpec(BaseModel):
         mark: Mark
         encodings: dict[Channel, Encoding] = {}
         layers: list[ChartSpec] = []
         raw_vega_lite: dict[str, Any] = {}   # escape hatch, merged last

     The escape hatch is the same trust-scoped pattern the codebase already uses
     twice — QuerySpec + the read-only /api/query/sql path, and
     AggregatePlan.derive for window functions. Consistency here is deliberate,
     not incidental.

     Resolution against the semantic layer — the part that earns the IR

     New backend/src/dataq/services/chart.py, resolve_chart(chart, 
     output_columns, profile) -> ChartSpec:

     - Validate every Encoding.field against the query's actual output columns.
       This is what kills the silent-empty-chart bug class, and it is exactly
       what raw Vega-Lite cannot give us.
     - Infer Encoding.type from the semantic type we already track, reusing
       SEMANTIC_TYPES.matches_any in core/semantic.py:
       - temporal / time.* → temporal
       - numeric / money.amount, or role == "measure" → quantitative
       - categorical / geo.country_iso2 / text → nominal
       - a time-part label column (a bucket with a sibling bucket_ord) →
         ordinal, auto-sorted by the ordinal column
     - That last rule fixes an existing latent bug for free:
       TimeBucket.ordinal_alias already emits bucket_ord precisely because "Thu"
       does not sort as text, and nothing currently uses it. The chart layer
       will.

     Compilation ChartSpec -> Vega-Lite happens in the frontend
     (frontend/src/renderers/vegaLite.ts), preserving the existing principle
     that the backend never renders and keeping a non-Vega renderer possible
     later. Validation stays on the backend, which is the side that has the
     profile.

     Back-compatibility

     VizSpec gains chart: ChartSpec | None alongside the existing spec: dict.
     Renderers prefer chart when present and fall back to spec. This matters
     because dashboards persist the recipe, not a snapshot — panels saved before
     this change must keep rendering. viz.map_points and viz.table keep their
     spec dict; only the Vega-Lite family ports over.

     The toggle, both directions

     - Chart → dataset. OperationRequest gains from_query: QuerySpec | None.
       With op="aggregate" and from_query set, run_aggregate_op skips
       plugin.plan() and materialises that query directly — every downstream
       step (derive wrapper, write_relation, add_version, and the pinned
       semantic-type inheritance that makes the result joinable) is reused
       unchanged. A "Save as dataset" button on any chart panel.
     - Dataset → chart. Teach suggest.viz to recognise aggregate-shaped datasets
       (a bucket/bucket_ord pair, an n/share pair) and propose the right
       default chart. A "Chart this" action on any aggregate.

     Chart inspector (answers "preview the data backing the chart")

        mounted during the build, so data cannot be baked into the image — it
        has to arrive at runtime.
     3. Railway injects a PORT env var and probes a healthcheck path before
        switching traffic.

     That maps onto your three requirements almost exactly: volume = requirement
     2, railway up = requirement 1, and the CLI's railway volume files upload =
     requirement 3.

     What is broken for Railway today

     - The container ignores $PORT. CMD is exec form with a hardcoded 8000; the
       JSON array form does not expand variables, so Railway's port is never

     Approach

     Topology

     Railway project
     └── service "dataq"          built from ./Dockerfile
         └── volume  →  /data     5 GB, persists across deploys
                         ├── catalog.sqlite        metadata (WAL)
                         ├── warehouse.duckdb      external-plugin cache
                         ├── lake/<ds>/v1/*.parquet
                         ├── uploads/
                         └── _inbox/               restore drop-box

     DATAQ_DATA_DIR=/data is already the Dockerfile default, so every path above
     lands on the volume. A code deploy replaces the container and leaves the
     volume untouched — that is requirement 2, for free.

     Getting data up: restore-on-boot

     railway volume files upload puts a file on the volume; something has to
     unpack it. That must happen before the app starts, because the app holds
     catalog.sqlite open in WAL mode and warehouse.duckdb open for the whole
     process lifetime — overwriting those under a live process risks corruption.
     So a new docker/entrypoint.sh:

     # if a bundle is waiting, restore it before uvicorn opens anything
     for bundle in "$DATAQ_DATA_DIR"/_inbox/*.tgz; do
       [ -e "$bundle" ] || continue
       [ "$DATAQ_RESTORE_MODE" = "replace" ] && find "$DATAQ_DATA_DIR" -mindepth
     1 \
           -not -path "$DATAQ_DATA_DIR/_inbox*" -delete
       tar xzf "$bundle" -C "$DATAQ_DATA_DIR"
       mv "$bundle" "$bundle.applied-$(date +%s)"   # idempotent across restarts
     done
     exec uvicorn dataq.api.app:app --host 0.0.0.0 --port "${PORT:-8000}"
     --app-dir backend/src

     replace gives you "reset"; the default merge gives you "override". Renaming
     the bundle afterwards means a restart does not redo the restore.

     Auth

     New backend/src/dataq/api/auth.py, one ASGI middleware:

     - Two settings: auth_token: str | None and require_auth: bool = False.
     - If require_auth is true and no token is set, the app refuses to start —
       railway.json sets DATAQ_REQUIRE_AUTH=true, so you cannot deploy it open
       by accident. Local dev is unaffected by default.
     - When a token is set, every /api/* needs Authorization: Bearer <token>,
       except /api/health (Railway probes it unauthenticated). Compared with
       hmac.compare_digest.
     - The SPA prompts once on a 401 and keeps the token in localStorage;
       frontend/src/api/client.ts attaches the header, and the existing ApiError
       path already surfaces a clean message.

     Plus two hardening fixes worth doing while we are here, both using code
     that already exists:

     - POST /api/sources/preview and op="import" accept an arbitrary uri that is
       never checked against the browse roots — it goes straight into
       read_csv(...). Route both through browse_service.resolve_within_roots,
       which already does the containment check correctly.
     - Set DATAQ_BROWSE_ROOTS=/data/uploads in Railway.

     Residual risk to accept knowingly: /api/query/sql is SELECT-only but DuckDB
     can still read_csv('/etc/passwd'). enable_external_access=false would fix
     it but also blocks read_parquet of the lake, so it is not available in
     parquet mode. Behind the token this is an authenticated-user risk, which is
     the right level for a single-user tool.

  On the reset design

  Rather than a DATAQ_RESTORE_MODE env var you'd have to set and unset, the
  bundle filename carries the intent: make data-replace produces
  dataq-data.replace.tgz, and .replace. is what tells the entrypoint to wipe
  first. A reset can't be caused by a variable someone set weeks ago, or missed
  because it was never set.

  specific reason: the running app holds catalog.sqlite open in WAL mode and
